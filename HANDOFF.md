## 3. Known environment/infra quirks

### 3.1 `uvicorn --reload` is flaky here

Hit this hard mid-session: after editing `products.py`/`schemas.py`, the reloader logged `Reloading...` but the running server kept serving stale routes. The stale worker process wasn't killable via `Stop-Process -Id <pid>` or `taskkill` using the PID reported by `Get-NetTCPConnection`/`Get-CimInstance`/`netstat -ano` — those all agreed on a PID that `Get-Process`/`taskkill` then claimed didn't exist. This machine has other users' processes visible via `ps -W` (a shared/multi-session terminal server), which is almost certainly why: the netstat-reported PID appears to be session-relative and doesn't resolve through the normal Windows process APIs from this session.

**What actually worked:** find the *real* PID from uvicorn's own log line (`Started server process [NNNNN]`) or from `ps -W` (look for the recently-started `python.exe` under this project's venv), then `taskkill /F /PID <that PID>`.

**Recommendation for next session:** don't run `--reload` for anything you're actively iterating on. Start uvicorn plain (`uvicorn app.main:app --port 8010`, no `--reload`), and after each batch of backend edits, kill and restart it manually, then `curl .../openapi.json` to confirm the routes you expect are actually registered before trusting the running server. This cost real time this session — don't rediscover it.

**2026-07-28 addendum:** hit this again restarting for the UAT work, and this time *neither* of the two documented workarounds resolved directly — `taskkill /F /PID <netstat PID>` said "not found", and so did `taskkill /F /PID <PID from uvicorn's own "Started server process [...]" log line>` (that log line turned out to be stale, from an earlier start in the same never-truncated log file, not the currently-listening process). What actually worked: `tasklist /FI "IMAGENAME eq python.exe"` — unlike `taskkill`, `tasklist` *does* enumerate other sessions on this shared terminal server and shows each PID's real `Session Name`/`Session#` — cross-referenced against `netstat -ano`'s listening PID for port 8010 to confirm it was a real, currently-running process, then `taskkill /F /PID <that PID>` succeeded immediately. So: if a specific PID gets a phantom "not found" from `taskkill`, don't assume it's dead — confirm with `tasklist /FI "PID eq <n>"` first; if `tasklist` sees it, `taskkill` should work on the same PID. (Bash-tool-specific note: Git Bash mangles `/F`/`/PID` as absolute paths — use `taskkill //F //PID <n>` with doubled slashes, or invoke via the PowerShell tool instead.)

### 3.2 Every `(str, Enum)` model field is a native Postgres ENUM — adding a value needs a migration, not just an edit

Adding `LifecycleStage.INFOSEC` and restarting the backend was **not** enough — the column is a real Postgres `ENUM` type (`\d product` shows `current_stage | lifecyclestage`, and `create_all()` only creates *missing* types, it never `ALTER`s an existing one). Trying to write `INFOSEC` into that column without first extending the DB-level enum would have failed at the SQL layer with an opaque error the first time anyone actually hit it, not at Python import time — easy to miss in dev if you don't specifically exercise the new value.

Fix now in place: `app/database.py`'s `_sync_lifecycle_stage_enum()` runs `ALTER TYPE lifecyclestage ADD VALUE IF NOT EXISTS '<value>' AFTER '<prev>'` for every member of `LIFECYCLE_ORDER` on every startup (idempotent, autocommit connection since `ADD VALUE` can't run inside an implicit transaction on older Postgres). **This same gotcha applies to every other enum in `models.py`** (`TaskStatus`, `BugStatus`, `Priority`, ...) — if Phase 2 adds a new bug status or UAT result, it needs the same `ALTER TYPE ... ADD VALUE IF NOT EXISTS` treatment, either by generalizing `_sync_lifecycle_stage_enum()` into a loop over all enum columns, or by finally moving to Alembic (PRD §8 already flags this as the eventual plan). Verified by checking `SELECT enumlabel FROM pg_enum WHERE enumtypid = 'lifecyclestage'::regtype` directly in psql before trusting it worked — don't just trust that the app didn't crash on startup.

### 3.3 *(2026-07-27)* This migration pattern is only needed for new columns/enum values on *existing* tables — brand-new tables don't need it

Worth being explicit about, since §3.2 reads like every schema change needs a `_sync_*` function and that's not true. The Infosec tables (`InfosecChecklistTemplate`, `InfosecChecklistItem`, `TaskAssignee`, ...) are entirely new tables with entirely new enums (`InfosecItemStatus`, `InfosecItemSource`) — plain `SQLModel.metadata.create_all()` handles those on first startup with zero extra code, because `create_all()` *does* create missing tables and missing enum types, it just never `ALTER`s ones that already exist. The `_sync_*` treatment in §3.2 is specifically for adding a column to a table `create_all()` already created in a previous run (`Task.stage`, `Task.brd_section`) or a value to an enum type it already created (`LifecycleStage.INFOSEC`). Know which case you're in before reflexively writing a migration function.

The multi-assignee change did still need one migration, but a data one, not a schema one: `_sync_task_assignees_backfill()` carries `task.assignee_id`'s existing values into the new `TaskAssignee` table (the old column itself is just left in Postgres, unmapped — no `DROP COLUMN`, consistent with this project's no-destructive-migrations stance).

## 4. Design system quick-reference (updated 2026-07-29)

- **Layout:** wrap every authenticated page in `<AppShell>`. Content goes in a `mx-auto max-w-{4xl|5xl|6xl} px-4 py-8..10` div.
- **Apple "Liquid Glass" system (2026-07-29):** the flat/no-shadow look is gone — the app now follows the `apple-design` skill's materials/type/motion model. Two distinct surface treatments, don't mix them:
  - **Solid elevated surfaces** (cards, kanban tiles, list rows) stay opaque (`bg-card`) and use the extended `.card-glow` class (`index.css`) — specular top highlight + hairline rim + real `--shadow-1` elevation. `components/ui/card.tsx`'s `Card` uses this by default.
  - **Translucent floating chrome** (header, sidebar, inputs/selects/textareas, segmented tab strips, modal sheets) uses `.glass` / `.glass-thin` / `.glass-thick` / `.glass-sidebar` (`backdrop-filter` + tint, `-webkit-` prefixed) — never stack two of these on top of each other.
  - New tokens in `index.css`: `--material-*-tint`/`--material-blur*` (materials), `--shadow-1`..`--shadow-4`/`--shadow-glass` (elevation), `--radius-2xl`/`--radius-capsule`, `--ease-apple-out`/`--ease-ios`/`--ease-snappy` + `--duration-instant/fast/base/slow` (motion) — all additive, existing tokens (`--background`, `--card`, `--border`, etc.) untouched.
  - Motion is CSS-only (no `motion`/GSAP dependency): buttons/interactive rows use `active:scale-[...]` for instant pointer-down feedback plus the new easing/duration tokens. Segmented controls (`components/ui/tabs.tsx`, `components/ModuleNav.tsx`) share chrome from `lib/segmentedControl.ts` and a sliding indicator from `lib/useSlidingIndicator.ts` (measures the active item's DOM rect, animates via `transform: translateX() scaleX()` only — never `width`).
  - `@media (prefers-reduced-motion: reduce)`, `(prefers-reduced-transparency: reduce)`, and `(prefers-contrast: more)` fallbacks now exist in `index.css` (previously entirely absent) — the transparency/contrast ones are scoped to the `.glass*`/`.card-glow` classes.
  - Type scale: `.text-title-3`/`.text-title-2`/`.text-headline` classes (own namespace, not bridged into Tailwind's `tracking-*`/`leading-*` since those are already used elsewhere with default values) — `CardTitle` uses `.text-headline`, every page's `<h1>` uses `.text-title-3`.
  - Repeated "selected row" idiom (BRD/Uat/Bugs) is now `lib/selectedRow.ts`'s `SELECTED_ROW_ACTIVE`/`SELECTED_ROW_INACTIVE` instead of an inline ternary in each file — reuse it for any new selectable-list page rather than re-inlining the classes.
- **Cards/Buttons/Inputs:** `components/ui/*` — `rounded-xl`, glass/elevation per above. `textarea.tsx`, `select.tsx` same conventions as `input.tsx`.
- **Colors:** semantic tokens only (`bg-background`, `text-muted-foreground`, etc.), never hardcoded hex/oklch — except SVG `stroke` props in `ArchitectureBoardTab.tsx` (React Flow edges can't take Tailwind classes), which use literal Apple system-color hexes.
- **Status badges (BRD/Task/Priority/Stage/Infosec item/UAT result/Bug status):** every status-badge map (`lib/stages.ts`, `lib/brdStatus.ts`, `lib/taskMeta.ts`, `lib/infosecMeta.ts`, `lib/uatMeta.ts`) writes out **literal, complete** Tailwind class strings per status — never `` `bg-${x}` `` string interpolation, or Tailwind v4's scanner won't generate the class and it silently renders unstyled. This bit an early session; keep following the pattern for any new status enum (a real bug board's own status map, when that gets built).
- **Kanban-style boards:** use `flex gap-3 overflow-x-auto` with fixed-width `shrink-0` columns, not CSS grid — see §2's bug fix above.
- **Badge shape as a second visual channel, not just color:** Priority is `rounded-full` (pill), Stage is `rounded-md` (tag) + its own icon — two badges that sit next to each other constantly (every task card/row) need a shape or icon difference, not just different colors, or they read as visually interchangeable. Apply the same logic before adding a third badge kind anywhere they'd co-occur.
- **Multi-select fields:** use the chip-picker pattern (`components/AssigneePicker.tsx`) — selected items as small removable chips + a `<Select>` beneath offering what's not yet picked. Not a native `<select multiple>` (bad UX) and not a checkbox list (doesn't scale). Reuse this component for any future multi-select field on a product-scoped entity; it takes `members`/`selectedIds`/`onChange` and doesn't care what entity it's attached to.
- **Cross-module navigation:** every module page renders `<ModuleNav productId={id} productName={product.name} active="<key>" />` right under the page-level back link — don't add a bare "back to product" `<Link>` to a new module page, use `ModuleNav` so the new module is reachable from every other one for free.
- **Draft-list-then-submit-all:** the pattern used for Planning's task breakdown and Infosec's checklist items — local `draft` state with `key`/`onChange`/`onRemove`, an "Add row" button, and a single submit that loops the existing single-create endpoint per row rather than adding a bulk-create endpoint. Reuse this shape for any future "build a batch of N things, then commit" UI rather than inventing a new one.
- **Icons:** `lucide-react`, `h-4 w-4` standard inline size (`h-3 w-3`/`h-3.5 w-3.5` inside compact badges).

## 5. Known gaps / honest TODOs

1. **BRD approval is single-reviewer, not multi-reviewer quorum.** PRD §6.2 describes "sign-off from designated reviewer(s)" with "PM sees outstanding reviewers at a glance" — v1 just lets any PM/Stakeholder/Admin approve unilaterally. No reviewer designation, no per-reviewer tracking. Flagged as an open question in PRD §12 — decide if Phase 2 needs this before building it.
2. **No delete/deactivate for anything** — products, tasks, diagrams, members are all append-only in the UI (the API doesn't expose deletes either, by design for now, but worth deciding deliberately rather than by omission). *(2026-07-27)* Now also true of Infosec checklist templates — the global "bank" only grows, no edit/delete/archive on a template or its items once created.
3. **Diagram versioning groups by exact title match.** Renaming a diagram's title effectively starts a new group/history — no rename-in-place. Minor, but worth knowing before someone reports "my version history disappeared."
4. **Sidebar keyboard shortcuts (`⌘D`/`⌘N`) are still decorative** — carried over from last session, still not wired to real `keydown` listeners.
5. **No mobile nav** — also carried over, `Sidebar` still has no drawer fallback below `md`.
6. ~~Global Admin role isn't fully reflected in the frontend.~~ **Resolved 2026-07-27.** `frontend/lib/types.ts::User.global_role` is now populated for the signed-in user (via `MeRead`) and `app/deps.py::get_member_product` bypasses for Admin server-side, so a pure global Admin (not a `ProductMember` anywhere) can now reach and use every page, not just have write actions accepted if they somehow got there. Verified end-to-end with a real Admin test user in this session's Infosec work.
7. **The "done + asterisk" flag is task-data-only, not a permanent watermark** (deliberate, see TL;DR) — so a non-task stage (Release, Post-production, or Infosec/UAT before anyone tags a task to them) that the product already passed will silently revert to plain gray "upcoming" if an earlier stage reopens, with no flag that it was ever reached. Fine for the case asked for; if Phase 2 wants "the product has *definitely* been in Release before" to survive a reopen regardless of tasks, that needs a persisted `max_stage_reached` column on `Product` (new enum-typed column → same `ADD COLUMN IF NOT EXISTS` migration pattern as §3.2/`_sync_task_stage_column()`).
8. **Reopening and auto-advancing only ever move exactly one step**, same as the manual advance-stage button — there's no cascading skip-ahead even if several consecutive stages are already fully cleared. A product sitting "current" at a stage with zero tasks and nothing pending still needs the manual "Advance to next stage" button; task completion alone won't carry it past an empty stage.
9. *(2026-07-27)* **`anthropic` and `gemini` AI providers are wired but not real-call-verified** — this dev environment has no API keys configured for either (`.env` has `AI_PROVIDER=gemini` active but `GEMINI_API_KEY=` blank as of this session's end). Only `mock` has actually been exercised end-to-end. Both real-provider code paths are covered for the *failure* case (missing key → clean `502`, not a crash) but not for real model output quality/shape — worth a real smoke test with a key before relying on either in a demo.
10. *(2026-07-27)* **Infosec Stage 1 → Stage 2 has no server-side gate.** A VAPT report can be uploaded (starting Stage 2) at any time regardless of Stage 1's completion state — the UI just orders Stage 1 above Stage 2 to suggest the intended workflow. Deliberate scoping call made during planning, not an oversight; revisit if a real gate turns out to matter.
11. *(2026-07-27)* **`TaskAssignee` has no "primary assignee" or role-within-task concept** — it's a flat, symmetric set. If a future feature wants a distinguished owner (e.g. "who does a notification go to first"), that needs a real field, not just "first row in the set" (insertion order isn't guaranteed meaningful).
12. *(2026-07-27)* **Infosec checklist item CSV import has no dedup/merge** — applying the same template to a product twice, or uploading two CSVs with overlapping titles into one template, just creates duplicate rows. No warning, no skip-if-exists. Matches this project's general "trust the PM, don't engineer around user error" stance elsewhere, but worth knowing if it becomes a real complaint.
13. *(2026-07-28)* **UAT feedback items have no comment thread and there's no cross-product UAT criteria template bank** — both deliberate scope cuts made when building the UAT module, not oversights. Infosec has both (comment thread on checklist items, global checklist bank); UAT's PRD spec (§6.5) reads as simpler ("Pass/Fail/Comment" per criterion, no discussion thread called for) and criteria are naturally BRD-sourced per cycle rather than reusable across products the way a security checklist is. Revisit if a real need for either shows up.
14. *(2026-07-28)* **`UATFeedback` was modeled as a mutable checklist-style item (one evolving result per criterion), not an append-only submission log** — the PRD's "stakeholders submit feedback per criterion" is genuinely ambiguous between "one current result" and "many independent submissions from different testers." The checklist reading was chosen for an unambiguous pass-rate calc and to reuse Infosec's exact detail-panel/activity-log pattern. If Phase 2+ wants multiple testers to each record their own independent Pass/Fail on the same criterion (rather than the last submitter's result winning), that's a data-model change, not a UI tweak — `UATFeedback` would need to split into a stable criterion identity plus a one-to-many submissions table.
15. *(2026-07-28)* **No dedicated Bug Tracking module yet** — `BugReport` rows now get created for real (via UAT's one-click Fail → Bug conversion), and are shown inline on the originating UAT feedback item (title/severity/status), but there's no bug board/kanban, no triage queue, no severity/status editing UI, and no listing endpoint beyond what UAT's `linked_bug` lookup needs. This is PRD §11's next roadmap item, explicitly scoped out of the UAT build (see TL;DR) — see §6 below.
16. *(2026-07-28)* **`bugreport.uat_feedback_id` has no DB-level foreign-key constraint** — added via a raw `ALTER TABLE ... ADD COLUMN` (see §3.2/§3.3's migration pattern), which doesn't declare `REFERENCES`, unlike columns SQLModel creates via `create_all()` on a fresh table. Same situation as `task.brd_section`/`task.stage` — enforced at the ORM/Python level only, not the database level. Consistent with the rest of this project's migration pattern, not unique to UAT, but worth knowing if something ever writes to these tables outside the API.
17. *(2026-07-28)* **Opening a UAT cycle can jump the lifecycle stage from `DEVELOPMENT` straight to `UAT`, skipping `INFOSEC` in one call** — `uat.py`'s `create_cycle` uses `frm={DEVELOPMENT, INFOSEC}` so it works as the natural "move forward" trigger from either predecessor stage without the caller needing to know which one the product is currently in. This is a deliberate convenience, but it's a different shape from the rest of the app's "advance exactly one stage at a time" convention (Known Gap #8, `advance_to_next_stage`/`maybe_advance_when_stage_cleared`). Matches the fact that Infosec already has no server-side gate stopping a product from reaching UAT without ever completing an Infosec checklist (Known Gap #10) — so this doesn't introduce a new hole, just a second way to fall into the existing one.

## 6. Suggested next steps

Per PRD §11, **Phase 2** is: UAT cycles + pass/fail feedback + one-click fail→bug conversion, bug tracking (triage/severity/status flow), post-production feedback (closes the lifecycle loop back to Intake), the richer visual dashboard (health tiles, full card-based timeline), and the notification center. **2026-07-28 update: UAT is now built** (see TL;DR) — Planning, Infosec, and UAT, all three originally listed as Phase-2-adjacent gaps, are now done, which changes the shape of what's left below.

Natural build order, following the same pattern established across this project's sessions (backend router + schemas → frontend module page → wire into `ProductDetail` → verify with curl then a driven browser session):

1. **Bug tracking is next** — the loop is now `DEVELOPMENT → INFOSEC → UAT → BUG_FIX`, and `BUG_FIX` is the next stage still without a real module (a product just sits there until a PM manually advances it). UAT's one-click Fail→Bug conversion already creates real `BugReport` rows (source=`UAT`, linked back via `uat_feedback_id`) and shows them inline on the originating feedback item — see Known Gap #15 — but there's no board/kanban, no triage queue, no severity/status editing, and no way to log a bug from Infosec or standalone ("Internal"/"Post-Production" sources per PRD §6.6 aren't reachable yet). Infosec's checklist-item detail panel (status dropdown + activity feed + comment thread, `Infosec.tsx`'s `InfosecItemDetail`) and UAT's simpler version (status dropdown + activity feed, no thread, `Uat.tsx`'s `FeedbackDetail`) are both reasonable templates for a bug detail panel — decide during design whether bugs want a comment thread (Infosec-style) or not (UAT-style). Closing out `BUG_FIX` (all bugs `Verified`/`Closed`) should presumably auto-advance to `RELEASE`, mirroring UAT's cycle-close → stage-advance wiring in `uat.py`.
2. **Real AI-provider smoke test** — get a working `GEMINI_API_KEY` (or `ANTHROPIC_API_KEY`) into `.env` and actually exercise Planning's "Suggest tasks" against a real model before this ships anywhere real; see Known Gap #9.
3. **Post-production feedback** — the last piece needed to close the lifecycle loop back to Intake (PRD §6.7/§5.9). No skeleton exists for this yet beyond `PostProductionFeedback` in `models.py` (unused, same situation `UATCycleModel`/`UATFeedback`/`BugReport` were in before this session).
4. Before starting any of the above: resolve Known Gap #1 (multi-reviewer BRD sign-off) only if it actually blocks something in Phase 2 — otherwise leave it, don't gold-plate Phase 1 retroactively. Same goes for Known Gaps #13/#14 (UAT's comment-thread and criteria-bank scope cuts) — only revisit if bug tracking or real usage surfaces an actual need.
